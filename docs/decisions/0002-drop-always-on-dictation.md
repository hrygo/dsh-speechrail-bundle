# ADR-0002：放弃「常驻听写 + 口令发送」模式

- 日期：2026-10-25
- 状态：Accepted（用户当日明确决策："决策，放弃"）
- 关联：[ADR-0001](0001-independent-speechrail-input.md)、[设计文档](../superpowers/specs/2026-10-23-speechrail-input-design.md) §2 反目标、[插件演进路线分析](../roadmap/2026-10-25-plugin-evolution.md)（放弃之后还剩什么、按什么顺序做）。
- 证据来源：本次会话的行业调研（VAD 与端点检测、常驻听写产品交互、浏览器常开采集平台约束、常开麦克风安全与无障碍惯例），核实日期 2026-10-25。调研结论未单独落盘；本 ADR 引用其中决定性的来源。

## 背景

用户提出一个新模式：开启后麦克风常驻，按 VAD 的停顿切段，每段的转写结果**追加**进输入框草稿（不逐段发送），用户单独说一句口令 `over` 时才把整条消息发给 agent；使用场景是"人在电脑前，手不在鼠标键盘上"。

该提议与[设计文档](../superpowers/specs/2026-10-23-speechrail-input-design.md) §2 的反目标（"不支持…常开麦克风或自动发送"、"结果进入原会话草稿，不自动提交给 Agent"）直接冲突，因此需要一次显式决策，而不是让它悄悄发生。

调研后用户决定放弃。

## 选项

| 维度 | A 完整常驻听写 | B 最小常驻 | C 不做（维持按次点击） | D 相邻路线：热键/按住说话 |
|---|---|---|---|---|
| 麦克风 | 常开 | 常开 | 按次 | 按次 |
| 分段 | Silero VAD v5/v6 + ONNX Runtime Web | 现有 RMS 阈值 | — | — |
| 提交 | 口令 `over` + 撤销窗口/二次确认 | 口令 `over` | 手动 | 手动 |
| 新增依赖 | ONNX 运行时 + 约 2.24 MB 模型 | 无 | 无 | 无（DOM 键盘监听） |
| 服务场景 | 手不在键鼠上 | 手不在键鼠上 | 通用 | 手在键鼠上 |
| 结论 | 放弃 | 放弃 | 采用（维持现状） | 另行评估，见后续路线文档 |

## 决定

放弃 A 与 B。不实现常驻麦克风、不实现口令提交、不引入 VAD 模型或 ONNX 运行时。设计文档 §2 的反目标维持不变。

## 理由

证据分级：**[文档]** 有来源与日期的公开文档；**[实测]** 本机或本仓库代码实测；**[推断]** 由证据推出的判断，未经实测。

1. **[文档] 唯一的直接先例是一次未落地的灰度。** 微信 8.0.61 于 2025-07 灰度"实时对讲"：语音按钮点亮后边说边把文字实时显示在输入框，**连说 "over over" 自动发送**，`over` 仅作触发、不进正文，要发字面 `over` 需连说三遍（[证券时报/界面新闻 2025-07-23](https://www.stcn.com/article/detail/2708964.html)）。其当前状态口径矛盾：客服称"已下线，暂无重新上线计划"（[IT之家](https://www.ithome.com/0/870/189.htm)、[光明网](https://m.gmw.cn/2025-07/24/content_1304091378.htm)），腾讯随后[否认下线、称按反馈持续调整](https://static.cdsb.com/micropub/Articles/202507/6514c7a76f1a8f8284a7dc2f5ea8b5e8.html)。可确证的是：未正式发布，结局不明。
2. **[文档] 灰度用户的反馈正落在本设计的价值假设上。** 内测用户认为"仅省去点击发送这一步，与原语音转文字功能差异有限"，且固定英文口令 `over` 不符合中文用户习惯，要求开放"发送/完毕"这类自定义口令（同上来源）。
3. **[文档] 口令与正文的分离在行业里有强共识，而 `over` 是最差的一类口令。** Talon、Apple Voice Control、Windows Voice Access 都用**独立模式**门控整套语法（[Talon modes](https://talonvoice.com/docs/reference/globals.modes.html)、[Apple mh40719](https://support.apple.com/guide/mac-help/use-voice-control-commands-mh40719/mac)、[Voice Access 命令表](https://support.microsoft.com/en-us/accessibility/windows/voice-access/voice-access-command-list)）；控制词必须**整段精确匹配、绝不做子串搜索**（[yazses 9e6c5552](https://github.com/MSKazemi/yazses/commit/9e6c5552247846458e7d64705ec2b2acdd997ae5) 记录了未加锚点的旧实现吞掉 6 个测试短语中的 4 个）；Wispr Flow 的 `press enter` 只在句尾、只在粘贴成功后触发，且默认关闭（[docs](https://docs.wisprflow.ai/articles/6391241694-use-flow-hands-free)）。`over` 是高频英文虚词，微信不得不加"连说两遍才触发、三遍才当正文"。
4. **[文档+推断] 一键提交与既有安全惯例正面冲突。** WCAG 2.2 SC 3.3.4 要求会改动用户数据的动作至少满足"可撤销/可检查/可确认"之一（[w3.org](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html)）；唤醒词类系统的误触发并非罕见（FakeWake 测量：50% 用户每周至少误触发一次，[arxiv](https://ar5iv.labs.arxiv.org/html/2109.09958)）；Gmail 的撤销窗口是 5/10/20/30 秒（[help](https://support.google.com/mail/answer/2819488)）。要安全就必须加撤销窗口或二次确认，用户想消除的"点点点"会以另一种形式回来（推断）。
5. **[文档] 纯静音端点检测已被托管厂商集体放弃。** Deepgram 因背景噪声使 VAD 看不到静音而增加按词时间戳的 `UtteranceEnd`；AssemblyAI 明说"不靠静音断句"；LiveKit 公开对比中纯 VAD 基线在 300 ms 延迟预算下误切句率 55.6%，其音频+语义模型 9.9%（厂商自测，排名仅供参考）。即**误切是必然**，"合并上一段"成为必需品而非可选项。
6. **[推断] 成本结构与目标场景不成比例。** 可靠 VAD 只有 Silero VAD（MIT，ONNX Runtime Web）站得住，代价是约 2.24 MB 模型加一个新运行时依赖，而本包发布体积约 64 KB / 36 个文件；退化到现有 RMS 则会在电视、风扇、音乐等稳定大音量下持续判定为说话。
7. **[实测] 该模式是服务"手不在键鼠上"的唯一形状。** 能听见口令的前提就是麦克风常开；放弃它等于接受该场景不服务。这是本决策被明确接受的代价。

## 代价与约束

- **接受"手不在键鼠上"这一场景不服务**，本插件继续只在用户可触达键鼠时工作。
- 放弃 A/B 后，"自用"路线上真正剩下的相邻路线是**热键/按住说话**（选项 D），它服务的是相反的场景（手在键鼠上），**不能替代**本模式。
- 本决策不改变设计文档 §2 的任何反目标；调研中确认的平台约束（麦克风权限可能是"仅此一次"、普通 `getUserMedia` 轨道不豁免标签页节流）不因放弃而失效，但它们约束的是未来任何常开方案。

## 复活条件

出现下列任一条件时重新评估本决策，而不是重新争论：

1. 本机引擎（SpeechRail 或其他）提供可用的流式/实时转写接口，使分段、静音计时与段落队列不必由本插件承担；
2. "手不在键鼠上"的使用频率被实测证明足够高（例如一段时间的计数，而不是印象）；
3. DSH 客户端提供正式的常开采集或快捷键扩展点，或上游愿意为第三方插件开放；
4. 出现可复用、许可明确、体积极小（或已在依赖树内）的浏览器端 VAD，使成本结构改变；
5. 出现"提交可撤销"的正式机制（例如消息在被 agent 消费前存在可撤回窗口），使第 4 条理由不再成立。
